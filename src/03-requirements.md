# 3. Требования

## 3.1. Stakeholder requirements

Формат: **SR-SH-x** — требования заинтересованных сторон. Уровень: что нужно пользователям и бизнесу в эксплуатации, без описания внутренней реализации.

1. **SR-SH-1 (Кладовщик — быстрая приёмка товара).** Система должна позволять кладовщику принимать товар на склад с использованием сканера штрихкодов или ручного ввода кода товара, чтобы сократить время приёмки и снизить вероятность ошибки.
2. **SR-SH-2 (Кладовщик — понятные задания).** Система должна предоставлять кладовщику пошаговые задания на приёмку, размещение, сборку, упаковку и инвентаризацию, чтобы сотрудник мог выполнять операции без постоянной помощи супервайзера.
3. **SR-SH-3 (Кладовщик — работа при плохой сети).** Система должна позволять продолжать выполнение заранее загруженных складских заданий при плохой сети или временной потере соединения.
4. **SR-SH-4 (Супервайзер — контроль операций).** Система должна позволять супервайзеру видеть текущие складские операции, статусы заданий, ошибки и спорные ситуации в одном интерфейсе.
5. **SR-SH-5 (Супервайзер — управление расхождениями).** Система должна позволять супервайзеру подтверждать или отклонять операции с расхождениями: недостача, излишек, неверная ячейка, повреждённый товар.
6. **SR-SH-6 (Менеджер логистики — контроль заказов).** Система должна предоставлять менеджеру логистики актуальный статус заказа из единого справочника статусов заказа: received, picking, picked, partial, supervisor_review, packing, awaiting_delivery_registration, awaiting_label, ready_to_ship, handed_to_carrier, cancelled. Статус заказа в интерфейсе менеджера логистики должен обновляться не позднее чем через 10 секунд после изменения статуса в WMS-lite при нормальной сети. 
7. **SR-SH-7 (Менеджер логистики — взаимодействие с доставкой).** Система должна поддерживать передачу данных заказа в курьерские службы и получение трек-номера для дальнейшего контроля доставки.
8. **SR-SH-8 (Служба поддержки — ответ клиенту).** Система должна позволять службе поддержки быстро получить информацию о состоянии заказа без обращения к кладовщику или супервайзеру.
9. **SR-SH-9 (Бизнес — точность остатков).** Система должна обеспечивать актуальный складской учёт по товарам и ячейкам, чтобы снизить риск продажи отсутствующего товара.
10. **SR-SH-10 (Бизнес — снижение ошибок сборки).** Система должна предотвращать ошибочную сборку заказов за счёт проверки товара, ячейки и состава заказа через сканирование.
11. **SR-SH-11 (Администратор — настройка склада).** Система должна позволять администратору настраивать пользователей, роли, зоны склада, ячейки, права доступа и параметры интеграций.
12. **SR-SH-12 (Аудит — история операций).** Система должна хранить историю складских операций, чтобы можно было восстановить действия пользователя при спорной ситуации или ошибке учёта.
13. **SR-SH-13 (Склад — инвентаризация).** Система должна поддерживать проведение инвентаризации по всему складу, отдельной зоне, ячейке или конкретному товару.
14. **SR-SH-14 (Операторы — удобство интерфейса).** Интерфейс системы должен быть простым для оператора склада, чтобы основные операции выполнялись быстро и без длительного обучения.
15. **SR-SH-15 (Бизнес — интеграция с OMS/ERP).** Система должна обмениваться данными с OMS/ERP: получать заказы, поставки и карточки товаров, а также передавать статусы складских операций.

## 3.2. System requirements

Формат: **SR-SYS-x** — системные требования. Атомарные, проверяемые, связанные со сценариями CONOPS.

### 3.2.0 Единый справочник статусов заказа

В WMS-lite используется единый справочник статусов заказа:

| Статус | Расшифровка |
| --- | --- |
| received | заказ получен из OMS/ERP |
| picking | заказ находится в сборке |
| picked | заказ полностью собран |
| partial | заказ собран частично из-за недостачи или проблемной позиции |
| supervisor_review | заказ ожидает решения супервайзера |
| packing | заказ находится на упаковке |
| awaiting_delivery_registration | заказ упакован, но ожидает регистрации в курьерской службе |
| ready_to_ship | заказ ожидает печати транспортной этикетки |
| awaiting_label | заказ готов к передаче курьеру |
| handed_to_carrier | заказ передан курьеру |
| cancelled | заказ отменён |

Все требования, сценарии CONOPS, API-контракты, Kafka-события, отчёты и тест-кейсы должны использовать только значения из справочника статусов заказа. Отображаемые пользователю русские названия статусов являются частью UI-ярлыков и не должны отличаться по смыслу от справочника статусов заказа.

1. **SR-SYS-1 (Авторизация пользователя).** Система должна позволять пользователю войти в WMS-lite через внешний IdP/SSO и получить сессию с ролью, переданной IdP/SSO. Система должна запрещать вход пользователю, если:
1. пользователь не найден;
2. учётная запись заблокирована;
3. роль пользователя не назначена;
4. IdP/SSO вернул отказ аутентификации;
5. срок действия токена истёк.                                                                Все успешные и неуспешные попытки входа должны сохраняться в аудит-журнале с указанием пользователя, времени, способа входа, результата и причины отказа.*Верификация:* функциональный тест успешного входа; негативные тесты отказа входа; инспекция аудит-журнала.
2. **SR-SYS-2 (Ролевой доступ).** Система должна ограничивать доступ к функциям в зависимости от роли пользователя: кладовщик, супервайзер, менеджер логистики, служба поддержки, администратор. *Верификация:* инспекция настроек ролей и функциональный тест доступа.
3. **SR-SYS-3 (Локальная копия справочника товаров).** Система должна хранить локальную read-only копию карточки товара, полученной из OMS/ERP, с атрибутами: ID товара, артикул, название, штрихкод, единица измерения и статус активности. Создание, изменение и удаление карточек товаров выполняется только в OMS/ERP. WMS-lite не должна позволять пользователям создавать или редактировать мастер-данные товара, за исключением локальных служебных признаков синхронизации *Верификация:* инспекция модели данных; интеграционный тест загрузки новой карточки товара из OMS/ERP; интеграционный тест обновления существующей карточки; негативный тест запрета ручного создания или редактирования карточки товара в WMS-lite.
4. **SR-SYS-4 (Структура склада).** Система должна хранить структуру склада, включающую зоны, ряды, ячейки и статус каждой ячейки. *Верификация:* инспекция БД и функциональный тест создания ячейки.
5. **SR-SYS-5 (Получение поставок из OMS/ERP).** Система должна принимать из OMS/ERP данные об ожидаемых поставках с перечнем товаров и ожидаемым количеством. *Верификация:* интеграционный тест загрузки поставки.
6. **SR-SYS-6 (Открытие задания на приёмку).** Система должна позволять кладовщику открыть задание на приёмку товара из списка доступных заданий. *Верификация:* функциональный тест открытия задания.
7. **SR-SYS-7 (Определение товара по штрихкоду).** После сканирования штрихкода система должна определить соответствующий товар из справочника. *Верификация:* функциональный тест сканирования существующего и неизвестного штрихкода.
8. **SR-SYS-8 (Ручной поиск товара).** Система должна позволять найти товар вручную по артикулу или названию, если штрихкод повреждён или не считывается. *Верификация:* функциональный тест ручного поиска.
9. **SR-SYS-9 (Сравнение количества при приёмке).** Система должна сравнивать фактическое количество товара при приёмке с ожидаемым количеством из задания. *Верификация:* функциональный тест приёмки с совпадающим и отличающимся количеством.
10. **SR-SYS-10 (Фиксация расхождения при приёмке).** Если фактическое количество товара отличается от ожидаемого, система должна создать запись о расхождении. *Верификация:* функциональный тест создания расхождения.
11. **SR-SYS-11 (Подтверждение расхождения супервайзером).** Система должна требовать подтверждения супервайзера для завершения приёмки с расхождением. *Верификация:* функциональный тест блокировки операции до подтверждения.
12. **SR-SYS-12 (Создание задания на размещение).** После успешной приёмки товара система должна создать задание на размещение принятого товара. *Верификация:* функциональный тест завершения приёмки и проверки созданного задания.
13. **SR-SYS-13 (Рекомендация ячейки размещения).** Система должна предлагать допустимую ячейку размещения с учётом типа товара, свободного места и правил хранения. *Верификация:* функциональный тест выбора ячейки для разных типов товаров.
14. **SR-SYS-14 (Проверка ячейки при размещении).** Перед размещением товара система должна требовать сканирования ячейки хранения. Если сканирование невозможно из-за недоступности или неисправности сканера, система может разрешить ручной ввод кода ячейки только пользователю с правом manual_override. Операция ручного ввода должна быть помечена как high_risk, содержать причину обхода сканирования и попадать в отчёт операций повышенного риска. *Верификация:* функциональный тест размещения с корректной и некорректной ячейкой; негативный тест ручного ввода без права manual_override; тест появления операции в отчёте повышенного риска.
15. **SR-SYS-15 (Проверка товара при размещении).** Перед подтверждением размещения система должна требовать сканирования товара или упаковки. Если штрихкод повреждён или сканер недоступен, система может разрешить ручной ввод артикула, внутреннего кода или штрихкода только пользователю с правом manual_override. *Верификация:* функциональный тест размещения правильного и неправильного товара; негативный тест ручного ввода без права manual_override; инспекция аудит-журнала.
16. **SR-SYS-16 (Обновление остатков по ячейке).** После подтверждения размещения система должна увеличить остаток товара в указанной ячейке на размещённое количество. *Верификация:* функциональный тест изменения остатков после размещения.
17. **SR-SYS-17 (Получение заказов из OMS/ERP).** Система должна принимать из OMS/ERP заказы на сборку с перечнем товаров, количеством и идентификатором заказа. *Верификация:* интеграционный тест загрузки заказа.
18. **SR-SYS-18 (Создание задания на сборку).** После получения заказа система должна создать задание на сборку для кладовщика. *Верификация:* функциональный тест появления задания после загрузки заказа.
19. **SR-SYS-19 (Маршрут сборки).** Система должна показывать кладовщику маршрут сборки по ячейкам, где находятся товары заказа. *Верификация:* функциональный тест отображения маршрута.
20. **SR-SYS-20 (Проверка ячейки при сборке).** Перед подбором товара система должна требовать сканирования ячейки, из которой берётся товар. Ручной ввод кода ячейки допускается только при недоступности сканера, наличии права manual_override и обязательном указании причины обхода сканирования. *Верификация:* функциональный тест блокировки подбора без сканирования ячейки.
21. **SR-SYS-21 (Проверка товара при сборке).** Перед добавлением товара в заказ система должна требовать сканирования товара. Ручной ввод допускается только при повреждённом штрихкоде или недоступности сканера, наличии права manual_override и дополнительном подтверждении выбранной карточки товара. *Верификация:* функциональный тест добавления товара после сканирования; негативный тест ручного ввода без права manual_override; тест попадания операции в отчёт повышенного риска.
22. **SR-SYS-22 (Блокировка неверного товара).** Если отсканированный товар не входит в состав заказа, система должна запретить добавление товара в заказ. *Верификация:* функциональный тест сканирования неверного товара.
23. **SR-SYS-23 (Частичная сборка и решение по заказу).** Если нужного количества товара нет на складе, система должна перевести заказ в статус «Частично собран» и создать инцидент для супервайзера. Супервайзер должен выбрать одно из решений: продолжить сборку после пополнения остатка, заменить ячейку или источник товара, разделить заказ на частичную отправку и отложенную позицию, отменить проблемную позицию, если это разрешено OMS/ERP, отменить заказ.После решения супервайзера система должна изменить статус заказа согласно справочнику статусов заказа и отправить событие wms.order.status_changed в OMS/ERP с указанием transitionReason.*Верификация:* функциональный тест partial-сборки; тест блокировки упаковки partial-заказа; тест выбора каждого решения супервайзером; интеграционный тест отправки transitionReason в OMS/ERP..
24. **SR-SYS-24 (Завершение сборки).** После подтверждения всех позиций заказа система должна перевести заказ в статус «Собран». *Верификация:* функциональный тест полной сборки заказа.
25. **SR-SYS-25 (Контрольное сканирование перед упаковкой).** Перед упаковкой заказа система должна позволять выполнить повторное сканирование товаров для проверки состава заказа. *Верификация:* функциональный тест контрольного сканирования.
26. **SR-SYS-26 (Блокировка упаковки при ошибке состава).** Если состав заказа при контрольном сканировании не совпадает с заданием, система должна запретить упаковку. *Верификация:* функциональный тест упаковки заказа с ошибочным составом.
27. **SR-SYS-27 (Регистрация отправления в курьерской службе).** Система должна передавать в курьерскую службу данные заказа, необходимые для регистрации отправления. *Верификация:* интеграционный тест передачи заказа в курьерскую службу.
28. **SR-SYS-28 (Сохранение трек-номера).** После успешной регистрации отправления система должна сохранить трек-номер, полученный от курьерской службы. *Верификация:* интеграционный тест получения и сохранения трек-номера.
29. **SR-SYS-29 (Печать этикетки).** После получения транспортной этикетки система должна отправить её на печать. *Верификация:* интеграционный тест печати этикетки.
30. **SR-SYS-30 (Повторная печать этикетки).** Система должна позволять повторно напечатать транспортную этикетку без повторной регистрации отправления в курьерской службе. *Верификация:* функциональный тест повторной печати.
31. **SR-SYS-31 (Создание задания на инвентаризацию).** Система должна позволять супервайзеру создать задание на инвентаризацию по складу, зоне, ячейке или товару. *Верификация:* функциональный тест создания задания на инвентаризацию.
32. **SR-SYS-32 (Сравнение фактических и учётных остатков).** Во время инвентаризации система должна сравнивать фактические остатки с учётными остатками. *Верификация:* функциональный тест инвентаризации с совпадением и расхождением остатков.
33. **SR-SYS-33 (Корректировка остатков).** Система должна требовать подтверждения супервайзера для применения корректировки остатков. *Верификация:* функциональный тест запрета корректировки без подтверждения.
34. **SR-SYS-34 (Журнал операций).** Система должна сохранять историю каждой складской операции с указанием пользователя, времени, товара, количества, ячейки и типа операции. *Верификация:* инспекция журнала после выполнения тестовых операций.
35. **SR-SYS-35 (Передача статусов в OMS/ERP).** Система должна передавать в OMS/ERP статусы приёмки, размещения, сборки, упаковки, отгрузки и инвентаризации. *Верификация:* интеграционный тест отправки статусов.
36. **SR-SYS-36 (Очередь повторной отправки).** Если внешняя система недоступна, WMS-lite должна поставить событие интеграции в очередь повторной отправки. *Верификация:* интеграционный тест при отключённой внешней системе.
37. **SR-SYS-37 (Статус синхронизации операции).** Система должна отображать статус синхронизации операции: «Синхронизировано», «Ожидает синхронизации», «Ошибка синхронизации». *Верификация:* функциональный тест отображения статусов.
38. **SR-SYS-38 (Уведомления о критичных ошибках).** Система должна уведомлять супервайзера о критичных ошибках: конфликт остатков, ошибка интеграции, сбой печати, расхождение при приёмке. *Верификация:* функциональный тест генерации уведомления.
39. **SR-SYS-39 (Отчёт по операциям).** Система должна формировать отчёт по складским операциям за выбранный период. *Верификация:* функциональный тест формирования отчёта.
40. **SR-SYS-40 (Администрирование настроек).** Система должна позволять администратору управлять пользователями, ролями, зонами склада, ячейками и настройками интеграций. *Верификация:* функциональный тест изменения настроек администратором.

## 3.3. NFR / качество с метриками

Формат: **NFR-x** — нефункциональные требования с измеримыми метриками.

1. **NFR-1 (Производительность сканирования).** При сканировании товара или ячейки система должна отображать результат операции не более чем за 1 секунду в 95-м перцентиле при нормальной сети. *Верификация:* нагрузочное тестирование с измерением p95 времени отклика.
2. **NFR-2 (Производительность складских операций).** Система должна обрабатывать не менее 3000 складских операций в час без отказа основных функций приёмки, размещения, сборки и упаковки. *Верификация:* нагрузочное тестирование.
3. **NFR-3 (Доступность серверной части).** Серверная часть WMS-lite должна иметь доступность не ниже 99,5 % в течение рабочих часов склада (по умолчанию — 06:00–22:00 локального времени, 7 дней в неделю; конкретный график фиксируется в SLA-соглашении), исключая запланированные окна обслуживания. *Верификация:* анализ эксплуатационных логов и SLA-отчёта (см. §3.4).
4. **NFR-4 (Offline-работа при плохой сети).** При потере сети мобильный интерфейс должен позволять продолжать выполнение заранее загруженных заданий не менее 4 часов. *Верификация:* демонстрация работы клиента при отключённой сети.
5. **NFR-5 (Скорость синхронизации после offline-режима).** После восстановления сети система должна синхронизировать до 1000 локально накопленных операций не более чем за 5 минут. *Верификация:* интеграционный тест синхронизации после offline-режима.
6. **NFR-6 (Точность операций со сканированием).** Доля операций размещения и сборки, выполненных через ручной ввод вместо обязательного сканирования, не должна превышать 1 % от общего числа операций размещения и сборки за смену.Каждая такая операция должна иметь: пользователя, роль пользователя, причину ручного ввода, тип операции, товар, ячейку, отметку high_risk, ссылку на исходное задание. *Верификация:* анализ журнала операций за тестовую смену; проверка отчёта операций high_risk; негативный тест операции без причины ручного ввода.
7. **NFR-7 (Запрет отрицательных остатков).** Система не должна допускать появление отрицательных остатков товара без отдельного подтверждения супервайзера. *Верификация:* функциональный тест попытки списания товара сверх доступного остатка.
8. **NFR-8 (Аудит операций).** История складских операций должна храниться не менее 12 месяцев. *Верификация:* инспекция политики хранения данных и проверка записей журнала.
9. **NFR-9 (Удобство обучения кладовщика).** Новый кладовщик должен иметь возможность выполнить базовую операцию сборки заказа после обучения длительностью не более 30 минут. *Верификация:* демонстрация на контрольной группе пользователей.
10. **NFR-10 (Количество экранных действий).** Основные операции кладовщика (приёмка, размещение, сборка, упаковка) должны выполняться не более чем за 5 экранных действий без учёта сканирования. *Верификация:* инспекция пользовательского сценария и UX-тест.
11. **NFR-11 (Одновременная работа пользователей).** Система должна поддерживать одновременную работу не менее 50 активных пользователей без превышения времени отклика 2 секунды в 95-м перцентиле для основных операций. *Верификация:* нагрузочное тестирование.
12. **NFR-12 (Повторная отправка событий интеграции).** При недоступности OMS/ERP или курьерской службы система должна выполнять повторную отправку событий не реже 1 раза в 2 минуты до успешной доставки или ручной отмены. *Верификация:* интеграционный тест недоступности внешней системы.
13. **NFR-13 (Восстановление после сбоя).** После аварийного перезапуска серверной части система должна восстановить очередь несинхронизированных операций без потери данных. *Верификация:* отказоустойчивый тест с принудительным перезапуском сервера.
14. **NFR-14 (Совместимость со сканерами).** Система должна поддерживать сканеры штрихкодов, работающие в режиме HID-клавиатуры. *Верификация:* демонстрация работы с HID-сканером.
15. **NFR-15 (Логирование критичных ошибок).** Критичные ошибки интеграций, печати, синхронизации и изменения остатков должны попадать в журнал не позднее чем через 10 секунд после возникновения события. *Верификация:* функциональный тест генерации критичной ошибки и проверки журнала.

## 3.4. Методика SLA

### 3.4.1. Что входит в «доступность» WMS-lite

Доступность считается по группам критичных операций, а не по всему приложению целиком. Если конкретная конечная точка API вне группы недоступна, это не считается простоем для SLA, но фиксируется в отчёте.

| Группа | Что входит | Критичность |
| --- | --- | --- |
| A — Операционные | Создание/чтение заданий, сканирование товара и ячейки, фиксация результата приёмки/размещения/сборки/упаковки | Высокая (целевая SLA 99,5 %) |
| B — Интеграционные | Регистрация отправлений у курьеров, передача статусов в OMS/ERP, печать этикеток | Средняя (целевая SLA 99,0 %) |
| C — Административные | Админ-интерфейс, отчёты, настройка справочников | Низкая (целевая SLA 98,0 %) |

### 3.4.2. Как считается аптайм

1. **Источник данных** — синтетические пробы из агента мониторинга (Prometheus Blackbox Exporter [5] или аналог) запускаются раз в 30 секунд для каждой группы операций.
2. **Критерий успеха пробы:** HTTP 2xx, время отклика ≤ целевого p95 группы, корректный response-payload.
3. **Минута считается «доступной»**, если ≥ 50% проб в минуте успешны для группы.
4. **Аптайм за период** = (доступные минуты / общие минуты периода) × 100%, рассчитывается за календарный месяц.
5. **Расчёт ведётся отдельно по каждой группе** A/B/C; итоговая SLA указывается по группе A (Operational).

### 3.4.3. Что исключается из расчёта

1. **Запланированные окна обслуживания**, согласованные не менее чем за 5 рабочих дней; не более 2 часов/месяц для группы A.
2. Сбои **внешних систем**, находящихся вне границ SoI (OMS/ERP, IdP, курьерские службы, почтовый сервер) — учитываются как «degraded mode», но не как простой WMS-lite. Фиксируются в отдельном разделе SLA-отчёта.
3. Сбои **клиентского устройства** (планшет, ТСД, сканер, локальная сеть склада).

### 3.4.4. Как считается p95 (для NFR-1, NFR-11)

1. **Источник** — серверный middleware замеряет длительность каждого запроса от приёма до ответа (без учёта сетевого пути до клиента).
2. **Окно агрегации** — скользящее 5-минутное окно; в отчёт идёт максимум окон за период, т. е. самый плохой 5-минутный интервал.
3. **Сценарии нагрузочного теста** должны воспроизводить: 50 одновременных активных пользователей (NFR-11); типичный микс — 60 % сканирование, 20 % открытие задания, 15 % подтверждение операции, 5 % поиск.
4. **Критерий прохождения NFR-1** — p95 сканирования ≤ 1 сек при нормальной сети (RTT клиент↔сервер ≤ 50 мс).

### 3.4.5. Что предъявляется как артефакт

1. **Ежемесячный SLA-отчёт** по группам A/B/C: аптайм, число инцидентов, длительность окон обслуживания, перечень внешних сбоев.
2. **Отчёт нагрузочного тестирования** перед релизом: профиль нагрузки, p50/p95/p99 по ключевым операциям, ошибки.
3. **Журнал инцидентов** с RCA для каждого нарушения SLA.
