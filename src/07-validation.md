## 7.3. Тест-кейсы

### TC-01 — E2E приёмка с расхождением и подтверждением супервайзера

**Цель.** Подтвердить SR-SYS-6, SR-SYS-7, SR-SYS-9, SR-SYS-10, SR-SYS-11, частично SR-SH-1, SR-SH-5.

**Предусловия.**

1. В OMS/ERP создана поставка S-100: товар «Кофе зерновой 1кг» = 50 шт.
2. Поставка загружена в WMS-lite (SR-SYS-5).
3. Пользователи: «Кладовщик1», «Супервайзер1» — авторизованы.
4. Сканер штрихкодов подключён к ТСД.

**Данные.** Товар: «Кофе зерновой 1кг», штрихкод 4607123456789. Ожидаемое количество: 50, фактическое: 48 (расхождение −2).

**Шаги.**

1. Кладовщик1 открывает задание на приёмку поставки S-100.
2. Сканирует штрихкод товара.
3. Вводит фактическое количество 48.
4. Подтверждает приёмку позиции.
5. Супервайзер1 открывает список расхождений.
6. Подтверждает расхождение с причиной «недогруз поставщика».

**Ожидаемые результаты.**

1. После шага 2 система определяет товар по справочнику и показывает ожидаемое количество 50.
2. После шага 4 фиксируется расхождение, операция получает статус «Требует подтверждения», запись на размещение не создаётся.
3. После шага 6 операция переходит в статус «Принят с расхождением», создаётся задание на размещение 48 единиц, в OMS/ERP уходит событие приёмки с разницей −2.
4. В аудит-журнале сохранены оба действия (Кладовщик1 — фиксация, Супервайзер1 — подтверждение).

### TC-02 — Приёмка при недоступном OMS/ERP (режим деградации)

**Цель.** Подтвердить SR-SYS-36, SR-SYS-37, режим деградации сценария 1, R-09 fallback.

**Предусловия.**

1. Поставка предзагружена в WMS-lite до отключения OMS/ERP.
2. OMS/ERP искусственно недоступна (заблокирован адаптер).
3. Кладовщик авторизован.

**Шаги.**

1. Кладовщик выполняет приёмку 10 позиций товара без расхождений.
2. Просматривает статус операции в UI.
3. Включает OMS/ERP обратно.
4. Через 2 минуты проверяет статус операции.

**Ожидаемые результаты.**

1. На шаге 1 операция фиксируется локально, в UI статус «Ожидает синхронизации».
2. Шаг 3: событие в Outbox.
3. Шаг 4: статус сменился на «Синхронизировано», в OMS/ERP пришло корректное событие приёмки.
4. Все события идемпотентны: повторная отправка не создала дубль.

### TC-03 — Размещение в неверную ячейку (негативный сценарий)

**Цель.** Подтвердить SR-SYS-12, SR-SYS-13, SR-SYS-14, SR-SYS-15.

**Предусловия.**

1. Товар принят (TC-01 завершён).
2. Создано задание на размещение 48 единиц.
3. Существуют ячейки A-01-01 (рекомендованная, сухая зона) и Z-99-99 (зона брака, недопустимо).

**Шаги.**

1. Кладовщик открывает задание.
2. Сканирует ячейку Z-99-99 вместо рекомендованной.
3. Сканирует товар.

**Ожидаемые результаты.**

1. После шага 2 система показывает предупреждение «Зона не подходит для данного товара» и блокирует размещение.
2. Операция не создаётся, остатки не меняются.
3. Запись о попытке появляется в журнале ошибок.

### TC-04 — Размещение в offline и обработка конфликта при синхронизации

**Цель.** Подтвердить NFR-4, NFR-5, SR-SYS-37, режим деградации сценария 2, R-01.

**Предусловия.**

1. Два кладовщика (К1, К2) с двумя ТСД, оба имеют задания на размещение в одну ячейку B-05-03 (вместимость 100 единиц).
2. К1 уходит в offline.
3. К2 онлайн.

**Шаги.**

1. К1 в offline размещает 80 единиц в B-05-03.
2. К2 онлайн размещает 70 единиц в ту же B-05-03.
3. К1 восстанавливает связь.
4. Супервайзер проверяет очередь конфликтов.

**Ожидаемые результаты.**

1. К2 успешно завершает операцию, остаток ячейки = 70.
2. После шага 3 синхронизация К1 поднимает конфликт: фактическая ёмкость превышена.
3. Операция К1 не применяется автоматически, попадает в очередь конфликтов супервайзера.
4. В UI обоих кладовщиков отображаются корректные статусы синхронизации.

### TC-05 — E2E сборка заказа по маршруту

**Цель.** Подтвердить SR-SYS-18, SR-SYS-19, SR-SYS-20, SR-SYS-21, SR-SYS-24, частично SR-SH-1, SR-SH-10.

**Предусловия.**

1. Заказ Z-200 из OMS/ERP: «Кофе 1кг» — 2 шт. из A-01-01, «Сахар 500г» — 1 шт. из A-03-02.
2. Остатки достаточны.
3. Кладовщик авторизован, ТСД онлайн.

**Шаги.**

1. Кладовщик открывает задание на сборку Z-200.
2. Идёт по маршруту: A-01-01.
3. Сканирует ячейку A-01-01.
4. Сканирует товар «Кофе 1кг», подтверждает количество 2.
5. Идёт к A-03-02.
6. Сканирует ячейку и товар «Сахар 500г», подтверждает 1.
7. Завершает сборку.

**Ожидаемые результаты.**

1. На шаге 1 в UI отображается маршрут с двумя ячейками в оптимальном порядке.
2. После шагов 4 и 6 позиции отмечены как собранные, остатки уменьшены.
3. После шага 7 заказ переходит в статус picked из справочника OrderStatus, в OMS/ERP уходит событие wms.order.status_changed с previousStatus = picking, newStatus = picked, создаётся задание на упаковку.
4. В аудит-журнале — последовательность сканирований с временной меткой.

### TC-06 — Блокировка сканирования неверного товара (негативный сценарий)

**Цель.** Подтвердить SR-SYS-22.

**Предусловия.**

1. Активно задание сборки Z-200 (товары как в TC-05).
2. В ячейке A-01-01 также лежит «Кофе 1кг другой бренд» (пересорт).

**Шаги.**

1. Кладовщик открывает задание.
2. Сканирует ячейку A-01-01.
3. Сканирует «Кофе 1кг другой бренд».

**Ожидаемые результаты.**

1. После шага 3 система блокирует добавление товара, показывает: «Этот товар не входит в заказ».
2. Запись о попытке появляется в журнале ошибок сборки.
3. Остатки и статус заказа не изменяются.

### TC-07 — Частичная сборка при недостатке товара

**Цель.** Подтвердить SR-SYS-23, R-05 fallback.

**Предусловия.**

1. Заказ Z-201: «Кофе 1кг» — 5 шт.; в ячейке A-01-01 фактически 3 шт. (учётный остаток был 5, но 2 шт. недостача).

**Шаги.**

1. Кладовщик собирает 3 шт.
2. Сканирует ячейку повторно, товара больше нет.
3. Отмечает «товар не найден».
4. Завершает сборку.

**Ожидаемые результаты.**

1. Заказ переходит в статус partial.
2. Создаётся инцидент для супервайзера с привязкой к ячейке A-01-01.
3. Планировщик создаёт задание циклической инвентаризации на A-01-01.
4. В OMS/ERP отправляется событие wms.order.status_changed с transitionReason = partial:not_enough_stock.

### TC-08 — Упаковка, регистрация в курьерской службе, печать этикетки

**Цель.** Подтвердить SR-SYS-25, SR-SYS-26, SR-SYS-27, SR-SYS-28, SR-SYS-29, SR-SH-7.

**Предусловия.**

1. Заказ Z-200 в статусе picked.
2. Курьерская служба «Тестовый курьер» доступна (заглушка), возвращает trackNumber TEST-12345.
3. Принтер этикеток доступен.

**Шаги.**

1. Упаковщик открывает задание упаковки Z-200.
2. Выполняет контрольное сканирование двух позиций.
3. Указывает вес 1.5 кг, габариты 30×20×15 см.
4. Подтверждает регистрацию отправления.
5. Проверяет факт печати этикетки.

**Ожидаемые результаты.**

1. После шага 2 состав совпал с заданием, шаг 3 разблокирован.
2. После шага 4 в Courier Adapter уходит запрос с idempotencyKey, ответ содержит trackNumber TEST-12345.
3. После шага 4 заказ переходит в статус ready_to_ship из справочника OrderStatus, в OMS/ERP уходит событие wms.order.status_changed с previousStatus = awaiting_label, newStatus = ready_to_ship, а событие содержит trackNumber.
4. На принтере распечатывается этикетка с trackNumber.

**Негативная ветка (SR-SYS-26).** Если на шаге 2 отсканирован третий, лишний товар — система блокирует упаковку с ошибкой «Состав не совпадает», заказ возвращается на проверку.

### TC-09 — Повторная печать этикетки без повторной регистрации

**Цель.** Подтвердить SR-SYS-30.

**Предусловия.**

1. Z-200 успешно зарегистрирован в курьерской службе (TC-08 пройден), но физическая этикетка повреждена.
2. Принтер доступен.

**Шаги.**

1. Упаковщик открывает заказ Z-200.
2. Нажимает «Повторить печать этикетки».

**Ожидаемые результаты.**

1. В курьерскую службу не уходит новый запрос регистрации (проверяется по логу адаптера и счётчику запросов).
2. Этикетка с тем же trackNumber TEST-12345 повторно отправляется на печать.
3. В аудите фиксируется событие повторной печати с причиной.

### TC-10 — Инвентаризация ячейки с расхождением и корректировкой

**Цель.** Подтвердить SR-SYS-31, SR-SYS-32, SR-SYS-33, SR-SH-13, SR-SH-9.

**Предусловия.**

1. Учётный остаток в ячейке A-03-02 = 20 «Сахар 500г».
2. Фактически в ячейке 17 шт.
3. Супервайзер1 авторизован.

**Шаги.**

1. Супервайзер создаёт задание инвентаризации на ячейку A-03-02.
2. Кладовщик открывает задание, сканирует ячейку и товар.
3. Вводит фактическое количество 17 до того, как UI показывает учётный остаток (см. меры по R-08).
4. Подтверждает.
5. Супервайзер видит расхождение −3 в очереди.
6. Подтверждает корректировку с причиной «недостача».

**Ожидаемые результаты.**

1. Шаг 3: UI не показывает учётный остаток до ввода факта.
2. Шаг 4: создаётся запись расхождения, остатки не меняются до подтверждения.
3. Шаг 6: остаток обновляется до 17, в OMS/ERP уходит событие корректировки, в журнале — причина и инициатор.
4. Без подтверждения супервайзером кладовщик не может изменить остаток (negative-проверка SR-SYS-33).

### TC-11 — Очередь повторной отправки при недоступном OMS/ERP

**Цель.** Подтвердить SR-SYS-36, SR-SYS-37, SR-SYS-38, NFR-12, R-09 fallback.

**Предусловия.**

1. OMS/ERP искусственно недоступна.
2. Подготовлены 5 операций: 2 приёмки, 1 размещение, 1 сборка, 1 инвентаризация.

**Шаги.**

1. Выполнить все 5 операций.
2. Проверить очередь Outbox — должно быть 5 необработанных событий.
3. Подождать 2 минуты, проверить лог повторных попыток.
4. Восстановить OMS/ERP.
5. Подождать до 2 минут.
6. Проверить состояние очереди и события в OMS/ERP.

**Ожидаемые результаты.**

1. Все 5 операций приняты локально, в UI у каждой статус «Ожидает синхронизации» (SR-SYS-37).
2. Лог содержит как минимум одну повторную попытку в первые 2 минуты (NFR-12).
3. Супервайзер получил уведомление «возраст самой старой операции в очереди > X» (SR-SYS-38).
4. После шага 6 очередь пуста, в OMS/ERP — все 5 событий ровно по одному разу (идемпотентность).

### TC-12 — Offline-режим 4 часа + синхронизация после восстановления

**Цель.** Подтвердить NFR-4, NFR-5, SR-SH-3.

**Предусловия.**

1. Кладовщик авторизован, в локальный кэш загружено задание с 1000 операциями.
2. ТСД отключается от сети после загрузки.

**Шаги.**

1. Выключить сеть.
2. Выполнить 1000 складских операций в течение 4 часов.
3. Восстановить сеть.
4. Зафиксировать время до полной синхронизации.

**Ожидаемые результаты.**

1. В течение 4 часов все 1000 операций успешно выполняются локально.
2. После восстановления связи синхронизация всех 1000 операций завершается ≤ 5 минут (NFR-5).
3. Не потеряна ни одна операция; идемпотентность подтверждена.

### TC-13 — Ролевой доступ и read-only для службы поддержки

**Цель.** Подтвердить SR-SYS-1, SR-SYS-2, SR-SH-8, SR-SH-12.

**Предусловия.**

1. Существуют пользователи всех 5 ролей.
2. Заказ Z-200 в финальном состоянии.

**Шаги.**

1. Кладовщик пытается открыть админ-интерфейс.
2. Кладовщик пытается через API подтвердить корректировку остатка.
3. Сотрудник поддержки делает запрос GET /api/v1/support/orders/Z-200.
4. Сотрудник поддержки пытается изменить статус заказа.

**Ожидаемые результаты.**

1. Шаг 1: 403 Forbidden.
2. Шаг 2: 403 Forbidden, попытка зафиксирована в аудите.
3. Шаг 3: 200 OK, корректный payload с timeline и текущим статусом.
4. Шаг 4: 403 Forbidden.

### TC-14 — Нагрузочный тест: 50 пользователей, p95 сканирования ≤ 1 сек

**Цель.** Подтвердить NFR-1, NFR-2, NFR-11.

**Предусловия.**

1. Тестовый стенд, идентичный продуктовому по характеристикам.
2. Заготовлены 50 виртуальных пользователей с готовыми заданиями.
3. Сеть стенда — RTT клиент↔сервер ≤ 50 мс.

**Шаги.**

1. Запустить профиль нагрузки: 50 одновременных пользователей, микс 60% сканирование / 20% открытие задания / 15% подтверждение / 5% поиск, длительность 30 минут.
2. Зафиксировать суммарное число операций.
3. Снять метрики p50/p95/p99 по каждой операции.

**Ожидаемые результаты.**

1. Число операций, выполненных за 30 минут тестового прогона, ≥ 1500 (что эквивалентно ≥ 3000 операций/час, NFR-2).
2. p95 сканирования ≤ 1 сек (NFR-1).
3. p95 других основных операций ≤ 2 сек (NFR-11).
4. Доля ошибок < 0.1%; отчёт нагрузочного теста сохранён как артефакт.

## 7.4. Критерии готовности V&V

1. Для каждого требования есть минимум один артефакт проверки.
2. Все тест-кейсы исполняются и проходят на тестовом стенде до приёмки.
3. Для NFR с метриками (NFR-1, NFR-2, NFR-3, NFR-4, NFR-5, NFR-11, NFR-12) есть зафиксированные отчёты с конкретными значениями.
4. SLA-отчёт за первый месяц после ввода в эксплуатацию используется как baseline для последующих периодов.
