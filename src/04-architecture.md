# 4. Архитектура

## 4.1. Декомпозиция на компоненты и сервисы

Архитектурный стиль системы — **модульный монолит на серверной стороне, мобильный клиент с приоритетом автономной работы (offline-first) и событийная шина для интеграций**. Полное обоснование каждого решения приведено в §4.2 в виде набора Architecture Decision Records (ADR), оформленных по шаблону MADR [6].

### 4.1.1. Серверная часть (внутри WMS-lite Core)

| Компонент / модуль | Обязанности |
| --- | --- |
| API Gateway / BFF | Единая точка входа для мобильного и web-клиентов, аутентификация запросов, маршрутизация, rate-limit, агрегация ответов |
| Auth Module | Делегирование аутентификации в IdP/SSO (OIDC), выпуск внутренних токенов, поддержка fallback PIN-сессии |
| Task Module | Формирование заданий приёмки/размещения/сборки/упаковки/инвентаризации, распределение по кладовщикам, отслеживание статусов и SLA выполнения |
| Receiving Module | Логика приёмки: сравнение факт/ожидание, фиксация расхождений, создание событий о принятом товаре |
| Putaway Module | Логика размещения: рекомендация ячейки, проверка совместимости товар/зона, обновление остатков по ячейкам |
| Picking Module | Логика сборки: маршрут по ячейкам, проверка соответствия товара заказу, поддержка частичной сборки |
| Packing & Shipping Module | Контрольное сканирование, расчёт габаритов, передача в курьерский сервис, обработка трек-номера и этикетки |
| Inventory Module | Создание и проведение инвентаризаций, фиксация расхождений, генерация корректировок |
| Stock Module | Единый источник истины по остаткам товара в ячейках. Все изменения остатков выполняются только через него; для разделения нагрузки чтения и записи применяется упрощённый вариант шаблона CQRS [7] (чтение — из реплик БД) |
| Sync Module (OMS/ERP) | Исходящие события статусов в OMS/ERP, входящая подписка на заказы/поставки/карточки товаров, идемпотентность по event_id, очередь повторной отправки |
| Courier Adapter Module | Адаптеры для разных курьерских служб (СДЭК, Boxberry, Почта России и т.п.); единый внутренний контракт, специфика — в адаптере |
| Label Print Module | Очередь печати, выбор принтера по зоне, повторная печать без повторной регистрации, обработка ошибок принтера |
| Notification Module | Уведомления супервайзеру о критических событиях (внутри приложения, по электронной почте), правила эскалации, защита от лавинной отправки уведомлений |
| Audit Module | Append-only журнал всех операций: кто, когда, что, какие поля изменились, корреляция с заданием |
| Reporting Module | Чтение из реплики БД, формирование отчётов по сменам, инвентаризациям, SLA, конфликтам синхронизации |

## 4.2. Ключевые архитектурные решения

Все ключевые архитектурные решения оформлены по шаблону MADR (Markdown Architectural Decision Records) [6]. Для каждого решения приведены: статус, дата, ответственные за принятие решения, контекст и постановка задачи, измеримые критерии выбора (Decision Drivers), рассмотренные альтернативы, итоговое решение и его последствия (положительные и отрицательные). Числовые значения целевых характеристик ссылаются на разделы §3.2 (System requirements) и §3.3 (NFR) настоящего документа.

### ADR-1. Модульный монолит как стиль серверной части

- **Статус:** accepted
- **Дата:** 2026-05-23
- **Ответственные за решение:** Технический архитектор, Владелец продукта

**Контекст и постановка задачи.** Требуется выбрать архитектурный стиль серверной части WMS-lite в условиях ограниченных операционных ресурсов (≤ 1 SRE-FTE), фиксированного срока выхода MVP (4 месяца) и относительно небольшой целевой нагрузки. Решение является архитектурным в строгом смысле: смена стиля после ввода в эксплуатацию требует переписывания границ модулей и миграции данных.

**Критерии выбора (Decision Drivers).**

- Максимальное количество одновременных активных пользователей: 50 (NFR-11).
- Целевая пропускная способность операций: ≥ 3000 операций в час (NFR-2).
- Максимальный срок выхода MVP: 4 месяца.
- Допустимый объём операционных ресурсов: ≤ 1 SRE-FTE на эксплуатацию серверной части.
- Допустимое время восстановления после сбоя серверного процесса (MTTR): ≤ 60 секунд.

**Рассмотренные альтернативы.**

- Модульный монолит (одно приложение, одна БД, чёткое модульное разделение, общая транзакционная граница).
- Микросервисная архитектура (по одному сервису на каждый домен §4.1.1).
- Сервис-ориентированная архитектура (3–5 укрупнённых сервисов: операции, интеграции, отчётность).

**Сравнение альтернатив.**

| Критерий | Модульный монолит | Микросервисы (10+ сервисов) | Сервис-ориентированная (3–5) |
| --- | --- | --- | --- |
| Срок до MVP | 4 мес | ≈ 8 мес | ≈ 6 мес |
| Операционные ресурсы | ≈ 1 SRE-FTE | ≥ 2,5 SRE-FTE + Kubernetes | ≈ 1,5 SRE-FTE |
| Транзакции по остаткам | в одной БД, ACID | saga-оркестрация | частично распределённая |
| MTTR при сбое одного домена | ≈ 30 с (рестарт процесса) | ≈ 0 (деградация одного сервиса) | ≈ 15 с |
| Масштабирование нагруженных модулей | вертикально | горизонтально | горизонтально |

*Источник оценок.* Значения «Срок до MVP», «Операционные ресурсы» и «MTTR» — экспертная оценка технического архитектора на основе проектной декомпозиции §4.1 и нормативов трудоёмкости команды; служебные предположения и расчёт фиксируются в отдельной таблице оценок (артефакт планирования).

**Итоговое решение.** Выбрана альтернатива «Модульный монолит» — она удовлетворяет всем числовым критериям выбора при ≈ в 2 раза меньших операционных затратах и сроке MVP, чем микросервисная архитектура. Критерий MTTR (≤ 60 с) удовлетворён со значением около 30 с; превышение по сравнению с микросервисной альтернативой принято как осознанный компромисс.

**Последствия.**

- **Положительные:** транзакции по остаткам выполняются в одной БД (без распределённых транзакций), эксплуатация требует ≤ 1 SRE-FTE, срок до MVP не превышает 4 месяца, общая стоимость владения по экспертной оценке архитектора ниже на ≈ 40 % по сравнению с микросервисной альтернативой (методика расчёта TCO — суммарные FTE на эксплуатацию × средняя ставка + стоимость кластерной инфраструктуры; см. таблицу оценок планирования).
- **Отрицательные:** масштабирование возможно преимущественно вертикально; горячие модули (печать, синхронизация) нельзя вынести в отдельный процесс без рефакторинга; MTTR при сбое серверного процесса составляет ≈ 30 секунд против ≈ 0 для микросервисов. Митигация: критичные интеграции развязаны через шину событий (см. ADR-3) и могут быть вынесены в отдельный процесс без изменения внутренних потребителей.

### ADR-2. Мобильный клиент с приоритетом автономной работы (offline-first)

- **Статус:** accepted
- **Дата:** 2026-05-23
- **Ответственные за решение:** Технический архитектор, Менеджер логистики

**Контекст и постановка задачи.** Требование NFR-4 фиксирует обязательное продолжение работы кладовщика не менее 4 часов при потере связи Wi-Fi. По опыту эксплуатации сопоставимых складов (металлические стеллажи, высокое хранение, плотная расстановка металлических конструкций) локальные провалы Wi-Fi-покрытия являются штатным явлением и отнесены в реестре рисков к категории P = 3 (см. R-01, §6.2). Решение является архитектурным: смена стратегии работы клиента после ввода в эксплуатацию требует изменения протокола синхронизации и хранения состояния.

**Критерии выбора (Decision Drivers).**

- Гарантированная длительность непрерывной работы клиента при потере связи: ≥ 4 часов (NFR-4).
- Время полной синхронизации 1000 локально накопленных операций после восстановления связи: ≤ 5 минут (NFR-5).
- Доля конфликтных операций при синхронизации (целевое): ≤ 0,5 % от общего числа операций за смену.
- Доля операций, выполненных без обязательного сканирования: ≤ 1 % за смену (NFR-6).

**Рассмотренные альтернативы.**

- Клиент с приоритетом автономной работы (offline-first): локальный кэш заданий и справочников, идемпотентные операции, очередь синхронизации.
- Клиент с обязательным онлайн-режимом (always-online) и повторными попытками при сбое (retry-on-fail).
- Гибридный клиент: при потере связи переходит в режим «только просмотр».

**Сравнение альтернатив.**

| Критерий | Offline-first | Always-online + retry | Гибридный (read-only) |
| --- | --- | --- | --- |
| Время непрерывной работы при потере сети | ≥ 4 ч (соответствует NFR-4) | 0 мин | 0 мин (работа блокируется) |
| Доля конфликтных операций | целевое ≤ 0,5 % | 0 % (нет offline-очереди) | 0 % |
| Сложность клиента (LOC, оценочно) | ≈ 1,5× базовой | базовая | ≈ 1,1× базовой |
| Соответствие NFR-4 | да | нет | нет |

*Источник оценок.* Оценки «Сложность клиента» и «Доля конфликтных операций» — экспертная оценка технического архитектора на основе типовой декомпозиции offline-агента (локальный кэш, очередь, протокол синхронизации, разрешение конфликтов) относительно реализации always-online.

**Итоговое решение.** Выбрана альтернатива «Offline-first» как единственная, удовлетворяющая обязательному критерию NFR-4 (≥ 4 часа автономной работы). Дополнительная сложность клиента и риск конфликтов синхронизации компенсируются мерами митигации.

**Последствия.**

- **Положительные:** выполнение NFR-4 (4 часа автономной работы); непрерывность работы склада при провалах Wi-Fi; устойчивость к сбоям сетевого оборудования.
- **Отрицательные:** по экспертной оценке архитектора, сложность клиента возрастает на ≈ +50 % LOC относительно always-online (за счёт локального кэша, очереди синхронизации и логики разрешения конфликтов); возможны конфликты синхронизации после восстановления связи; локально кэшируемые справочники могут устаревать. Митигация: идемпотентные операции (operation_id генерируется на клиенте, см. §5.1); экран разрешения конфликтов для супервайзера; TTL локального кэша справочников; ограничение критичных операций в автономном режиме (см. R-01, §2.3 пункт 3).

### ADR-3. Событийная интеграция через Apache Kafka и шаблон Transactional Outbox

- **Статус:** accepted
- **Дата:** 2026-05-23
- **Ответственные за решение:** Технический архитектор, Владелец интеграции OMS/ERP

**Контекст и постановка задачи.** Интеграции с OMS/ERP, курьерскими службами и сервисом печати — внешние, периодически недоступные. Требования SR-SYS-36 и NFR-12 фиксируют гарантированную доставку событий и частоту повторных попыток. Требование §5.5 фиксирует партиционирование событий по ключу (productId) для сохранения порядка событий по одному товару. Решение является архитектурным: смена шины событий после ввода в эксплуатацию требует миграции схем и потребителей.

**Критерии выбора (Decision Drivers).**

- Гарантия доставки события при сбое издателя: at-least-once, 0 потерянных событий.
- Частота повторных попыток при недоступности внешней системы: ≥ 1 раза в 2 минуты (NFR-12).
- Время логирования критичной ошибки интеграции: ≤ 10 секунд (NFR-15).
- Сохранение порядка событий по ключу (productId): обязательно (§5.5).
- Поддержка эволюции схемы сообщений (обратная совместимость): обязательна.
- Срок хранения событий (для повторного потребления и восстановления): ≥ 7 суток.

**Рассмотренные альтернативы.**

- Apache Kafka [1] + Transactional Outbox [8] в PostgreSQL.
- RabbitMQ + Transactional Outbox в PostgreSQL.
- Синхронные REST-вызовы с повторными попытками в каждом модуле.

**Сравнение альтернатив.**

| Критерий | Kafka + Outbox | RabbitMQ + Outbox | Синхронный REST + retry |
| --- | --- | --- | --- |
| Гарантия доставки при сбое издателя | at-least-once (потери = 0) | at-least-once (потери = 0) | потери до 100 % при сбое модуля |
| Сохранение порядка по ключу | partition by key, нативно | через consistent-hash exchange (плагин) | не гарантируется |
| Срок хранения | настраиваемый (≥ 7 суток) | до подтверждения потребителем (события удаляются) | нет хранения |
| Поддержка эволюции схемы | Confluent Schema Registry с режимом BACKWARD [9] | требует внешних соглашений | требует версионирования API |
| Операционные накладные | 3 брокера × 4 vCPU | 2 узла × 2 vCPU | 0 дополнительных узлов |

**Итоговое решение.** Для целевой архитектуры выбрана альтернатива «Apache Kafka + Transactional Outbox», так как она обеспечивает at-least-once доставку, ретенцию событий не менее 7 суток, партиционирование по ключу и эволюцию схем.

Для MVP допускается поэтапное внедрение:
1. Transactional Outbox в PostgreSQL является обязательным уже в MVP;
2. публикация событий может выполняться через managed Kafka или через упрощённый outbox-worker, если эксплуатация собственного Kafka-кластера превышает ограничение ≤ 1 SRE-FTE;
3. переход на собственный Kafka-кластер допускается после подтверждения нагрузки, роста числа потребителей событий или появления требования к повторному воспроизведению событий за период более 7 суток. 

Ограничение: выбранный MVP-вариант не должен нарушать SR-SYS-36, NFR-12 и требования идемпотентности потребителей.

**Последствия.**

- **Положительные:** гарантированная доставка событий (at-least-once); идемпотентность на стороне потребителей по eventId; развязка во времени между WMS-lite и внешними системами; устойчивость к сбоям OMS/ERP (см. R-09).
- **Отрицательные:** требуется эксплуатация кластера Kafka (3 брокера × 4 vCPU); согласованность между WMS-lite и OMS/ERP — итоговая (eventual consistency); необходим мониторинг запаздывания потребителей. Митигация: для пользователя добавлены явные статусы синхронизации (SR-SYS-37); превышение порога запаздывания потребителя приводит к уведомлению по NFR-12; ретенция событий установлена в 7 суток для возможности повторного воспроизведения. Дополнительная митигация для MVP: если команда эксплуатации не готова сопровождать собственный Kafka-кластер, используется managed Kafka или временная реализация публикации через PostgreSQL Outbox + worker. Решение о переходе на собственный Kafka-кластер принимается после нагрузочного тестирования и оценки фактической операционной трудоёмкости.

### ADR-4. Единый источник истины по остаткам — Stock Module

- **Статус:** accepted
- **Дата:** 2026-05-23
- **Ответственные за решение:** Технический архитектор

**Контекст и постановка задачи.** Остатки товара изменяются из всех операционных доменов (приёмка, размещение, сборка, упаковка, инвентаризация). При независимой записи остатков из каждого домена возможны рассинхронизация инвариантов (например, отрицательный остаток) и расхождения между фактическим и учётным остатком (см. R-05, R-08, R-09). Решение является архитектурным: оно фиксирует границы единственного компонента, имеющего право изменять остатки.

**Критерии выбора (Decision Drivers).**

- Целевая пропускная способность операций изменения остатка: ≥ 3000 операций в час (NFR-2).
- Время ожидания блокировки строки в PostgreSQL при изменении остатка: p95 ≤ 50 мс.
- Запрет отрицательных остатков без подтверждения супервайзера (NFR-7) — должен проверяться единообразно во всех точках изменения.
- Полнота аудит-журнала: каждое изменение остатка имеет инициатора, время, операцию-источник (SR-SYS-34).

**Рассмотренные альтернативы.**

- Stock Module как единственный путь изменения остатка (команды + событие stock.updated в outbox).
- Распределённая запись: каждый домен пишет остатки самостоятельно в общую таблицу.
- CRDT-подход с устранением конфликтов на уровне типа данных.

**Сравнение альтернатив.**

| Критерий | Stock Module | Распределённая запись | CRDT |
| --- | --- | --- | --- |
| Единое место проверки инварианта «без отрицательного» | да | нет (повтор в каждом домене) | частично (зависит от типа CRDT) |
| Точка отказа | Stock Module («горячая точка») | нет единой точки | нет единой точки |
| Аудит изменения остатка | в одном месте, полная корреляция | разбросан по доменам | сложен для трассировки |
| Время ожидания row-level lock [10] | ≈ 5–50 мс при NFR-2 | сопоставимо | блокировок нет, но возможны конфликты разрешения |
| Соответствие NFR-7 | да | требует дублирования логики | нет (не гарантируется) |

**Итоговое решение.** Выбрана альтернатива «Stock Module». Она единственная даёт единое место проверки инварианта NFR-7 и единое место аудита, при сопоставимой латентности с распределённой записью.

**Последствия.**

- **Положительные:** единая логика проверки инвариантов; полный аудит изменений остатков; устранение источника расхождений (R-09).
- **Отрицательные:** Stock Module становится точкой повышенной нагрузки и требует оптимизации блокировок. Митигация: партиционирование таблицы остатков PostgreSQL по cell_id [10] (горизонтальное распределение конкурентных запросов); мониторинг времени ожидания row-level lock с целевым p95 ≤ 50 мс; уведомление при превышении.

### ADR-5. Локальный вход по PIN-коду при недоступности SSO/IdP

- **Статус:** accepted
- **Дата:** 2026-05-23
- **Ответственные за решение:** Технический архитектор, Администратор системы

**Контекст и постановка задачи.** Согласно R-10, недоступность внешнего IdP полностью блокирует вход пользователей в систему и, как следствие, останавливает склад. Требуется механизм входа, не зависящий от внешнего IdP, при сохранении приемлемого уровня безопасности. Решение является политикой безопасности и одновременно архитектурным: оно определяет компонент Auth Module и его поведение в режиме деградации.

**Критерии выбора (Decision Drivers).**

- Окно действия PIN после последнего успешного входа через SSO: ≤ 30 дней.
- Срок действия PIN-сессии: ≤ 8 часов.
- Доступные права в режиме деградации: 100 % группы A (Операционные), 0 % группы B (Интеграционные), 0 % группы C (Административные) — согласно §3.4.1.
- Алгоритм хранения PIN: должен соответствовать NIST SP 800-63B [11] и рекомендациям OWASP Password Storage Cheat Sheet [12] (memory-hard, фактор стоимости ≥ 12 для bcrypt или argon2id).

**Рассмотренные альтернативы.**

- PIN-сессия с ограниченным TTL и сокращёнными правами для пользователей, недавно входивших через SSO.
- Ожидание восстановления SSO без локального fallback.
- Постоянный локальный пароль для каждого пользователя.

**Сравнение альтернатив.**

| Критерий | PIN с TTL | Ожидание SSO | Локальный пароль |
| --- | --- | --- | --- |
| Время простоя склада при сбое IdP | 0 (работа продолжается) | до восстановления IdP | 0 |
| Поверхность атаки | расширена на 30 дней TTL | базовая (SSO) | расширена постоянно |
| Соответствие NIST SP 800-63B [11] | да (bcrypt cost ≥ 12) | неприменимо | требует политики ротации |
| Покрытие прав в fallback | только группа A | нет | возможно полное (риск) |

**Итоговое решение.** Выбрана альтернатива «PIN с TTL». Это единственная альтернатива, удовлетворяющая одновременно требованию непрерывности (0 простоя) и принципу минимизации поверхности атаки (TTL 30 дней; права только группы A).

**Последствия.**

- **Положительные:** непрерывность работы склада при недоступности внешнего IdP; независимость от внешнего поставщика аутентификации в режиме деградации; полное логирование действий в fallback-режиме для пост-инцидентной верификации.
- **Отрицательные:** расширение поверхности атаки на период действия PIN; риск компрометации PIN. Митигация: PIN хранится в виде хэша bcrypt с cost factor ≥ 12 — в соответствии с OWASP Password Storage Cheat Sheet [12] и общими требованиями NIST SP 800-63B [11] к хранению удерживаемых в памяти аутентификаторов; PIN действителен только при подтверждённой ранее SSO-аутентификации в течение последних 30 дней; режим деградации явно отображается в UI; для роли супервайзера активация PIN требует подтверждения второго фактора; все действия в fallback-режиме отдельно помечаются в аудит-журнале и подлежат сверке после восстановления SSO.

### ADR-6. PostgreSQL как основная СУБД

- **Статус:** accepted
- **Дата:** 2026-05-23
- **Ответственные за решение:** Технический архитектор

**Контекст и постановка задачи.** Требуется выбрать основную СУБД для хранения товаров, ячеек, остатков, заданий, операций, пользователей и аудит-журнала. Выбор является архитектурным: Stock Module (ADR-4) явно опирается на ACID-транзакции и row-level lock конкретной СУБД, а Transactional Outbox (ADR-3) — на единый транзакционный контур с прикладной БД; доступ к данным не унифицирован за абстрактным репозиторием, поэтому миграция между СУБД после ввода в эксплуатацию требует не только переноса данных, но и адаптации запросов и пересмотра гарантий конкурентного доступа.

**Критерии выбора (Decision Drivers).**

- Поддержка ACID-транзакций для операций над остатками (ADR-4).
- Поддержка row-level lock с предсказуемым временем ожидания: p95 ≤ 50 мс.
- Поддержка партиционирования таблиц по ключу (для масштабирования таблицы остатков).
- Поддержка реплик для разделения чтения и записи (CQRS-light в §4.1.1).
- Открытая лицензия (без отчислений) и наличие коммерческой поддержки на рынке РФ.

**Рассмотренные альтернативы.**

- PostgreSQL 16+ [10].
- MySQL 8 / MariaDB.
- Microsoft SQL Server Standard.

**Сравнение альтернатив.**

| Критерий | PostgreSQL | MySQL/MariaDB | MS SQL Server |
| --- | --- | --- | --- |
| ACID, MVCC | да | да | да |
| Партиционирование таблиц | декларативное по ключу | декларативное | декларативное |
| Стоимость лицензии в год (на 1 ядро) | 0 ₽ | 0 ₽ | от 250 000 ₽ |
| CTE и оконные функции | да | да | да |
| MATERIALIZED VIEW | да | нет | да (Indexed View) |
| Поддержка стандарта SQL:2016 (CTE, window functions, MATERIALIZED) | да | нет | частично |
| Доступность коммерческой поддержки в РФ | да | да | нет |

**Итоговое решение.** Выбрана PostgreSQL 16+. Она удовлетворяет всем критериям при нулевой стоимости лицензии и доступной коммерческой поддержке на рынке РФ.

**Последствия.**

- **Положительные:** нулевая стоимость лицензии; полная поддержка ACID-транзакций и партиционирования, требуемых ADR-4; единая платформа для основной БД и таблицы Outbox (ADR-3).
- **Отрицательные:** для горизонтального масштабирования (свыше одного primary-узла) требуется внешнее решение (например, Citus); ответственность за резервное копирование и восстановление полностью лежит на эксплуатации.
